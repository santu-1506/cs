Experiment No. 3: Testing IoT Device Security

Aim: To analyze security weaknesses in a simulated IoT device by identifying open ports, running services, service version disclosure, default/weak authentication, and unencrypted communication.

Procedure Steps

Step 1: Deploy Vulnerable IoT Simulation

Run the vulnerable web application (OWASP Juice Shop) using Docker on the Windows host system. Open Command Prompt and execute the following command:

docker run -d -p 8090:3000 --name juiceshop bkimminich/juice-shop

The application can now be accessed locally at http://localhost:8090.

Step 2: Identify Host IP Address

Find the IP address of the Windows machine hosting the Docker container to simulate scanning an IoT device over a LAN. In Command Prompt, run:

ipconfig
Step 3: Perform Network Scan from Kali Linux

Switch to the Kali Linux attacker machine. Perform a port scan, service detection, version detection, and banner grabbing against the target IP address using Nmap:

nmap -sV 192.168.0.148
Step 4: Analyze Nmap Version Scan (-sV) Results

Review the output from the Nmap scan. Look for:

  • Open ports (e.g., Port 8090 running HTTP)
  • Service fingerprints / version detection (identifying it as Juice Shop)
  • Other exposed Windows system ports (135, 139, 445)
Step 5: Accessing the IoT Device Web Dashboard

Open a web browser and navigate to the simulated IoT device's dashboard using the target IP and discovered port:

http://localhost:8090
Step 6: Testing Default/Weak Credentials

Test the login functionality to check for default or weak password vulnerabilities. Attempt to log in using common administrator credentials.

Step 7: Inspect Network Traffic (Developer Tools)

Open the browser's Developer Tools and navigate to the Network Tab.

  • Observe the HTTP requests being made.
  • Verify that the communication is running over plain HTTP.
  • Note that data is transmitted in plain text without SSL/TLS encryption.

EXERCISE: LOG FILE ANALYSIS FOR INCIDENT DETECTION LAB

Aim: To analyze system log files and detect suspicious activities such as failed login attempts and identify suspicious IP addresses .

Objectives

  • Understand system log files .
  • Detect suspicious activities and incidents .
  • Analyze logs using Linux tools .
  • Identify attack patterns (failed logins, brute force, etc.) .

Requirements & Tools

  • Kali Linux/Ubuntu VM .
  • Basic Linux command knowledge .
  • Tools: Kali Linux, journalctl, ssh, grep, awk, sort, less, cat .

Understanding Log Files

Navigate to Log Directory
cd /var/log
ls

The /var/log directory contains system and application logs such as Apache, Nginx, and login records used for security analysis .

  • dpkg.log: package activity .
  • apache2: web server logs .
  • nginx: web logs .
  • journal: system logs (IMPORTANT) .
  • wtmp, btmp: login records .

Log Analysis Commands

Successful Logins (wtmp)
last

Capture: Login history . This displays successful login sessions . It helps identify legitimate and suspicious user access .

System Logs using journalctl
journalctl | less

The journalctl command provides centralized system logs including authentication, services, and system events . Capture: Logs output .

Failed SSH Attempts
journalctl | grep "Failed"
SSH Login Activity
journalctl | grep ssh

This shows failed authentication attempts, which may indicate unauthorized access attempts . It also displays SSH-related logs, including login attempts and connections .

Error Detection
journalctl | grep -i error

Highlights system errors, which may indicate abnormal behavior or system issues .

Apache Log Analysis
cd /var/log/apache2
ls
sudo less access.log

Apache logs record web requests . These logs help identify suspicious web activity such as repeated requests or attacks .

Suspicious Requests:

grep "404" /var/log/apache2/access.log

This shows failed web requests (404 errors), which may indicate scanning or probing attacks .

Package Activity
less /var/log/dpkg.log

This shows software installation and update logs, useful for detecting unauthorized changes .

Real-Time Monitoring
sudo journalctl -f

This shows real-time system log monitoring, allowing detection of incidents as they occur .

Quick Checklist

Check Command Suspicious If
Failed logins lastb Many attempts
SSH activity journalctl | grep ssh -
Login history last Odd timing
Errors journalctl | grep error -
Web logs grep 404 Many failed requests

Step-by-Step Analysis of Your Log

  • 1. System Services (NORMAL): Finished phpsessionclean.service . Finished systemd-tmpfiles-clean.service . These are routine background tasks . No issue . Regular system maintenance services were observed, indicating normal system operation .
  • 2. CRON Jobs (NORMAL): CRON: session opened for user root . (root) CMD (debian-sal) . Automated scheduled task . Runs periodically . Scheduled cron jobs were observed, which are normal automated system processes .
  • 3. Your Own SUDO Activity (NORMAL): kali: COMMAND=/usr/bin/less access.log . kali: COMMAND=/usr/bin/journalctl -f . This is YOU running commands . Not suspicious . Sudo activity corresponds to legitimate administrative actions performed by the user .
  • 4. XFCE/GUI Services (NORMAL): xfconfd.service started . Desktop environment service . Normal .
  • 5. IMPORTANT PART (Repeated Kernel Messages): dndHGCM: Received message HOST_DND_FN_GH_REQ_PENDING . dnd: No guest source window . These lines are: Repeated MANY times , Coming from VirtualBox (VBoxDRM / DnD) . Is This Suspicious? Technically: NOT an attack . But abnormal repetitive behavior . Why it matters: Repeated logs = unusual system activity . Could indicate: Misconfiguration , Resource issue , VirtualBox interaction problem .

METHOD 1: Simulate Failed SSH Login

Step 1: Ensure SSH is Installed
sudo apt install openssh-server -y
Step 2: Start SSH Service
sudo service ssh start
Step 3: Find Your IP Address
ip a

Look for something like: inet 192.168.x.x

Step 4: Attempt Wrong Login (Generate Failures)
ssh fakeuser@localhost
# OR
ssh kali@localhost

Enter wrong password multiple times (5-10 times) .

Now Analyze Logs

Step 5: Check Failed Logins
journalctl | grep "Failed password"

You should now see: Failed password for kali from 127.0.0.1 port .

Step 6: Extract Suspicious IP
journalctl | grep "Failed password" | awk '{print $11}'

Output: 127.0.0.1 .

Step 7: Count Attempts Per IP
journalctl | grep "Failed password" | awk '{print $11}' | sort | uniq -c | sort -nr

Example: 10 127.0.0.1 .

How To Identify "Suspicious IP"

Simple rule :

  • Same IP repeated many times → Suspicious .
  • Unknown IP → Suspicious .
  • High frequency attempts → Brute force .
